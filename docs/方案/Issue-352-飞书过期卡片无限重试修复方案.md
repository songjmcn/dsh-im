# Issue 352 飞书过期卡片无限重试修复方案

日期：2026-10-13（Asia/Taipei）。基线：dsh-im 4.38.1。状态：已实施，自动化检查和本机真实飞书验收通过。

[Issue 352](https://github.com/xmanrui/dsh-im/issues/352) 的核心问题是：飞书卡片已经无法更新，mirror 恢复逻辑仍把它当作可以恢复的任务，反复请求且跨重启保留。修复集中在飞书 Bridge，复用现有状态存储、按会话串行队列和 30 秒定时器，补上清理条件、失败上限和单条恢复。

## 已确认的问题

mirror 是同步到飞书的某轮进度卡片的持久化快照。正常渲染会保存快照，卡片成功收尾后删除；更新失败时保留快照供恢复。

修复前存在四处问题：

1. `#finishStepCard()` 会把实际更新错误降为 `null`，恢复调用方无法区分临时断网和消息永久过期。
2. `#sealOrphanMirrors()` 只在成功后清理；失败就继续安排 30 秒后的检查，没有永久失败、过期或失败次数上限。
3. 每条记录各有一个恢复定时器，但每个回调都扫描全部记录，多条坏记录会重复发起请求。
4. 普通轮次的卡片失败后，即使协调器通过文本补发成功，旧卡片快照仍保留，重启后重新恢复。文本补发和卡片收尾目前是两个独立结果。

方案阶段先用真实 Bridge 代码、模拟飞书接口及模拟时钟复现；下表为修复前结果。实施后的真实飞书验收见文末。

| 场景 | 修复前结果 |
| --- | --- |
| 保存一条 27 天前的快照，接口持续返回过期错误 | 模拟 30 分钟后共请求 61 次，记录未清理 |
| 重新创建 Bridge 并沿用原状态 | 立即再次请求该卡片 |
| 卡片失败，最终答案通过文本补发成功 | 旧 mirror 仍在，普通轮次的记录等到重启后恢复 |
| 两条失败记录 | 启动请求 2 次，随后每 30 秒增加 4 次请求 |
| 同一卡片再次成功渲染 | `claimedAt` 随之刷新，并非创建时间 |

现有 session-sync 测试 24 项通过，但没有覆盖永久过期和有界恢复。本方案的验收用例需要断言修复后的行为，不能直接把上述确认缺陷的断言当作回归测试。

## 实现方案

### 保留实际错误并识别消息过期

在现有 Bridge 中增加一个小型过期判定函数，读取 SDK 异常的 `error.response.data.msg`、`error.message` 和直接业务错误的 `msg`。仅匹配明确的过期提示，例如 `Message has expired when updating message` 或 `Message can only be updated within fourteen days`，忽略大小写。

Issue 隐去了错误码，本次不猜测数值错误码，也不把所有 HTTP 400 都视为消息过期。结构化错误码仍应保留，方便日志和后续扩展。

具体沿用现有发送路径的写法：

1. `#patchStepCard()` 遇到业务响应非零 code 时，参考 `#replyStepMessage()`，在 Error 上保留 `code`、`feishuCode` 和可识别的错误文字；SDK 抛出的异常保持原样。
2. `#renderStepCardNow()` 标记 `card.broken` 时，同时保存原始错误到卡片的一个内部字段，例如 `lastError`。
3. `#finishStepCard()` 成功仍返回 `{ ok: true, cardIds }`；有卡片但失败时返回 `{ ok: false, error }`；没有卡片时仍可返回 `null`。已有正常回复调用方通过 `result?.ok` 判断，继续走原有文本和附件回退。
4. 恢复调用方使用 `result.error` 做分类，只有没有原始错误时才使用通用失败描述。已证明最终答案完整可见的 `answerVisible` 成功分支保持原语义。

普通轮次或重启后接管的轮次在收尾时遇到明确过期错误，也直接清理该 mirror 的持久化记录。保留当前轮次的内存结果回执，让原有协调器继续执行文本回退；不把“清理旧卡片”伪装成“答案已成功送达”。

### 复用 claimedAt 做保守的过期清理

增加固定常量 `MIRROR_STALE_MS = 14 * 24 * 60 * 60_000`，不增加用户配置。

`claimedAt` 的实际含义是最后一次成功保存卡片快照的时间。虽然不能据此精确计算卡片创建年龄，但可以安全用于保守判断：最后一次成功更新已经过去 14 天，则这张卡片的发送时间只会更早。在正常时钟条件下，可以直接放弃它的恢复，不必先查历史或调用飞书。

判断方向必须明确：

- `now - claimedAt >= MIRROR_STALE_MS`：直接清理孤儿恢复记录，不发起恢复请求。
- `claimedAt` 较新：不代表卡片未过期，仍由飞书的过期错误兜底。
- 老记录缺少有效时间戳，或时间戳明显位于未来：首次恢复时将已有 `claimedAt` 初始化为当前时间并持久化，作为有限保留期的起点。只初始化一次；以后轮询和失败不能刷新它。此时不声称知道卡片的真实创建时间。

保留现有“已被当前运行轮次接管”的检查，后台孤儿恢复不抢占活跃卡片。14 天规则是孤儿快照的保留上限，不是 AI 轮次的执行超时。活跃轮次真实遇到更新过期时，按错误分类处理。

### 重试只处理当前记录

给现有 `#sealOrphanMirrors()` 增加一个可选 key 参数即可：

- 启动时不传 key，处理当前持久化记录。
- 失败后的定时回调传当前 key，只处理该记录。
- `#finishSessionSyncMirror()` 已有的恢复排程同样传当前 key。

保留 `#scheduleMirrorCheck()` 的 30 秒间隔、同 key 去重和运行时取消机制。保留 `#queueEventTask(sessionId, ...)` 的串行执行方式，不引入另一套队列。

队列任务真正开始时，重新读取该 key 对应的当前记录，再检查是否已经删除、被接管或到达清理条件。定时回调只捕获 key，不携带可能过时的整份 entry。这样，清理后的排队任务不会重新写回旧记录，计数也不会被旧快照覆盖。

### 为恢复失败设置持久化上限

建议固定 `MIRROR_RECOVERY_MAX_FAILURES = 20`。沿用 30 秒间隔，在持续快速失败的情况下，约 10 分钟结束这条恢复任务。这里限制的是恢复失败次数，不限制活跃轮次的事件处理。

每条 mirror 仅新增一个可选字段 `recoveryFailures`：

- 老记录没有该字段时按 0 处理。
- 历史读取抛错，或已知结束轮次的卡片更新失败，消耗一次恢复失败预算。
- 通过 `setMirror(key, { ...currentEntry, recoveryFailures })` 保存，不修改 `claimedAt`、卡片 ID、正文和快照。
- 未达到 20 次时，用现有定时器安排当前 key 的下一次恢复。
- 达到 20 次时，清理记录和定时器，并记录一次放弃原因。启动恢复也要先检查计数，避免重启重置预算。
- 历史请求成功但无法确认轮次结束，不算更新失败，不封存卡片；继续原有检查，受孤儿快照保留期约束。一次无终态的查询不重置之前的失败预算。
- 恢复成功后清理记录。若记录被活跃轮次接管且卡片成功渲染，现有新快照写入自然重新开始失败预算。
- 运行时被取消时直接退出，不记恢复失败，也不继续排程。

本次保留固定间隔，直接使用次数上限结束无效工作，不额外实现退避策略和可配置重试器。未知错误在预算内保留恢复机会，明确过期错误则立即结束。

### 统一清理恢复记录和定时器

在 Bridge 内用一个小型私有方法集中处理恢复收尾，复用现有 Map 和 `clearMirror()`：

1. 取消并删除 `recovery\0${key}` 对应的恢复定时器。
2. 调用 `clearMirror(key)` 删除持久化记录。
3. 对过期或达到上限的清理，输出一条包含 `sessionId`、`turn`、原因和失败次数的日志；正常恢复成功不额外报警。

当前轮次自己的检查定时器仍由既有收尾逻辑负责取消。清理方法不删除会话绑定、聊天历史或飞书消息，也不清除仍被协调器使用的结果回执。孤儿恢复过程中出现的卡片内存对象沿用 `#finishStepCard()` 的释放行为。

失败日志取结构化错误中的有效说明，不打印整份 SDK 响应和完整答案。终止后不再每 30 秒输出同一错误。

## 行为决策

| 状态 | 处理 |
| --- | --- |
| 记录已经删除或运行时停止 | 退出，不请求、不排程 |
| 记录已由当前轮次接管 | 交给原有活跃路径处理 |
| 孤儿快照已超过 14 天保留期 | 清理，无历史查询和飞书更新 |
| 历史读取成功，但无法确认终态 | 不封存，不计失败，按原间隔检查 |
| 恢复卡片成功 | 清理记录与恢复定时器 |
| 明确返回消息过期 | 立即清理，不消耗后续重试 |
| 其他恢复错误且预算未耗尽 | 保存失败次数，30 秒后仅恢复该条 |
| 恢复失败达到 20 次 | 清理并记录放弃原因 |

达到失败上限意味着放弃旧卡片补写，已有飞书内容保留，未补写的尾部内容可能仍不完整。这是有界恢复的明确取舍；DSH 会话历史、AI 执行结果和当前正常文本回退不受此计数限制。此次不在恢复失败时另发新消息，以免重启补发历史答案造成重复通知。

纯文本补发成功后是否立即清理所有旧卡片，是另一项回执联动改动。本次保留现有行为，让旧记录通过上述保留期、错误分类和次数预算结束，不改协调器或共享注册表。

复用现有测试 fixture、`t.mock.timers` 和 StateStore 临时目录测试，不新增测试框架，不等待真实 14 天，也不依赖飞书凭据。

| 用例 | 修复后的预期 |
| --- | --- |
| 27 天前的有效孤儿快照 | 启动即清理，历史查询和更新请求均为 0 |

| claimedAt 较新，但 SDK 在 response.data.msg 返回过期错误 | 更新至多一次，然后清理；推进时钟不再请求 |
| 直接业务错误或 Error.message 携带过期提示 | 同样结束，验证大小写兼容 |
| 普通 HTTP 400、临时断网、超时 | 不误判为过期，预算内保留并重试 |
| 运行中渲染先失败，收尾时 card.broken | 保留原始过期原因；普通最终答案仍按原机制回退 |
| 短暂失败后恢复正常 | 使用原卡片完成更新，成功后清理，无重复补发 |
| 连续恢复失败达到 20 次 | 清理；继续推进时钟没有新请求 |
| 重载实际状态文件 | recoveryFailures 保留，重启不重新获得 20 次预算 |
| 两条记录同时失败 | 每个检查周期各尝试一次，共 2 次；不会互相重复扫描发请求 |
| 记录清理后仍有旧回调排队 | 不发请求，不重新保存记录 |
| 历史没有终态或查询结果被截断 | 不提前封存，不把正常等待算失败；过保留期后清理孤儿记录 |
| 缺失或无效 claimedAt 的老记录 | 只初始化一次；失败不续期，过期错误仍可立即结束 |
| 只有 lastContent 的旧快照及多张卡片快照 | 两种现有恢复分支都应用分类和预算；任一卡片明确过期后停止该次恢复 |
| 正常 IM、文本回退、已送达答案判定、运行时取消 | 保持既有测试行为，取消不增加失败次数或触发晚到重试 |

实施时先补会失败的关键用例，覆盖旧快照、真实错误结构、计数跨重启和多记录请求量；再改 Bridge，最后补齐边界用例。
